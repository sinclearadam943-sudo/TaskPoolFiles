# 统一配置管理系统设计

## 系统概述

统一配置管理系统管理所有服务、所有环境的配置，支持版本控制、热更新、加密存储、权限管理。

## 核心功能

### 数据模型

```
- 应用 (Application)
  └── 环境 (Environment)  (dev/staging/production)
      └── 配置键 (Key)
          └── 版本历史 (Version)
```

每个配置修改都生成新版本，可以随时回滚到历史版本。

## 配置结构

配置按 **应用 + 环境** 隔离：

| 应用 | 环境 | 配置文件 |
|------|------|----------|
| user-service | dev | 所有开发环境配置 |
| user-service | production | 所有生产环境配置 |
| payment-service | production | 支付服务生产配置 |

## 版本控制和回滚

每次配置修改保存新版本，记录：
- 修改人
- 修改时间
- 修改说明
- 对比变更内容

回滚：一键回到任意历史版本

```
GET /api/config/{app}/{env}/history → 列出所有版本
POST /api/config/{app}/{env}/rollback/{version} → 回滚
```

## 热更新和动态加载

两种通知方式：

1. **长轮询**：客户端连接服务器，配置变更了立刻推送
2. **定时拉取**：客户端每隔几秒拉一次，简单可靠
3. **webhook**：配置变更调用服务webhook通知

客户端拿到新配置后自动热更新，不需要重启服务。

## 配置加密

敏感配置（数据库密码、API密钥）加密存储：

- 加密密钥保存在服务端，不会出现在代码里
- 只有有权限的服务才能解密读取
- 即使配置文件泄露，拿到的也是密文

示例：
```yaml
database:
  password: encrypted:abcdef123456...
```

## 权限管理

权限控制粒度：
- 应用级权限：哪些人/服务能访问这个应用配置
- 环境级权限：开发能读不能改生产配置
- 敏感字段级权限：敏感配置只有指定服务能读

角色示例：
- **管理员**：可以改任何配置
- **开发者**：可以改开发环境，读预发布，不能改生产
- **运维**：可以改所有配置
- **服务**：只能读自己应用的配置

## 配置验证

保存配置之前先做验证：

1. **格式验证**：JSON/YAML格式正确
2. **类型验证**：字段类型正确（int/string/bool）
3. **必填验证**：必填字段不能为空
4. **范围验证**：数字在合理范围

验证不通过不让保存，避免错误配置导致服务出问题。

## 最佳实践

1. **配置不在代码里**：配置和代码分离，不同环境不同配置
2. **敏感信息不明文**：数据库密码API密钥一定要加密
3. **修改留痕迹**：谁改了什么什么时候都要有记录
4. **能回滚**：改错了能一键回滚，减少故障时间
5. **最小权限**：每个服务只能读自己需要的配置
